루퍼스 7주차 기록: Outbox에 저장한 이벤트부터 잘못되었다면

Outbox에 저장한 이벤트부터 잘못되었다면

1. 상황과 고민

6주차에는 주문은 확정되었지만 Kafka로 이벤트를 보내기 전에 서버가 종료되는 상황을 고민했습니다. consumer가 중복을 잘 처리하더라도, 처음부터 전달되지 않은 이벤트는 처리할 수 없었습니다.

이번 과제에서는 이 구간을 다루기 위해 Transactional Outbox를 적용했습니다. 주문 확정과 함께 발행할 이벤트를 DB에 저장하고, 별도의 relay가 Kafka로 전달하도록 변경했습니다.

이제 전송에 실패하거나 서버가 재시작되어도 DB에 남은 이벤트를 다시 찾을 수 있게 되었습니다. 다만...저장한 이벤트를 그대로 다시 보내도록 구현하다 보니, 다른 상황이 궁금해졌습니다.

실제 주문 수량은 2개인데 producer의 버그로 Outbox에는 20개가 저장되었다면 어떻게 해야 할까 싶었습니다.

아직 발행하지 않았다면 수량을 수정하고 보내면 될 것 같기도 했습니다. 하지만 timeout으로 발행 여부를 알 수 없거나, consumer가 이미 20개로 구매 활동을 저장했다면 Outbox만 수정해서는 해결되지 않을 것입니다.

특히 현재 consumer는 같은 주문의 확정 내용이 달라지면 충돌로 처리합니다. 같은 eventId로 수량을 바꾸어 다시 보내는 것은, 제가 구현한 재시도의 전제와도 맞지 않았습니다.

그래서 멘토님께 원본 이벤트와 이미 반영된 업무 결과를 실무에서는 어떤 절차로 정정하는지 질문드렸습니다. 발행되지 않은 것이 확실한 경우에도 Outbox 원본을 수정하지 않는지 함께 여쭤보았습니다.

2. 이번에 Outbox로 바꾼 범위

6주차의 발행 흐름은 다음과 같았습니다.

주문 확정 DB 커밋
  → AFTER_COMMIT listener 실행
  → Kafka 전송

주문이 롤백되었는데 확정 이벤트만 나가는 상황은 피할 수 있었지만, 커밋 직후 전송 전에 종료되면 발행할 대상이 DB에 남지 않았습니다.

이번에는 주문 확정과 Outbox 저장을 같은 로컬 DB 트랜잭션으로 묶었습니다.

하나의 DB 트랜잭션
  주문 확정
  재고 예약 소비
  OrderConfirmed 이벤트를 Outbox에 저장
  커밋

별도의 relay
  PENDING 조회
  저장된 이벤트를 Kafka로 전송
  broker의 성공 응답 확인
  별도 DB 트랜잭션에서 PUBLISHED 저장

Outbox 저장에 실패하면 로컬 주문 확정도 함께 롤백됩니다. 반대로 커밋에 성공했다면, relay가 아직 실행되지 않았더라도 발행할 내용은 DB에서 찾을 수 있습니다.

Transactional Outbox는 이런 DB 변경과 메시지 발행 사이의 이중 쓰기 문제를 다루는 패턴으로 이해했습니다. 다만 relay가 중복으로 전송할 수 있으므로 consumer의 멱등성도 함께 필요합니다. AWS Transactional outbox pattern

여기서 함께 롤백되는 범위는 로컬 DB의 변경입니다. 이미 외부 PG에서 성공한 결제까지 되돌아가는 것은 아닙니다. 로컬 확정에 실패하면 기존 거래를 조회하여 결과 반영을 다시 시도하고, PG 결제를 새로 생성하지 않는 흐름은 유지했습니다.

또한 relay는 발행할 때마다 현재 상품을 조회하여 이벤트를 다시 만들지 않습니다. 최초 확정 시각과 주문 품목으로 만든 JSON을 Outbox에 저장하고, 재시도에서도 그 내용을 그대로 전송하도록 했습니다.

같은 주문을 다시 전달하면서 현재 시각이나 변경된 상품 정보를 넣으면, 처음 확정된 사실과 다른 내용이 될 수 있기 때문입니다.

3. 같은 이벤트가 Kafka에 두 번 기록되어도 괜찮을까

Outbox를 적용해도 Kafka 전송과 PUBLISHED 저장이 하나의 트랜잭션이 되는 것은 아닙니다. 다음과 같은 구간은 남아있습니다.

1. Outbox의 이벤트를 Kafka로 전송
2. broker의 성공 응답 확인
3. PUBLISHED를 저장하기 전에 실행 중단
4. DB에는 PENDING이 남음
5. 다시 실행한 relay가 같은 이벤트를 재발행

PENDING이라고 해서 Kafka에 없는 이벤트라고 단정할 수 없는 이유입니다. 우리 DB에 발행 완료가 기록되지 않았을 뿐, Kafka에는 이미 기록되어 있을 수 있습니다.

이번 실험에서는 실제 주문 API와 로컬 PG, MySQL, Kafka, consumer를 연결했습니다. 첫 번째 발행에서 broker의 성공 응답을 확인한 뒤, PUBLISHED를 저장하기 전에 예외를 발생시켜 relay 흐름을 중단했습니다. 이후 같은 DB를 사용하는 새 relay로 재발행했습니다.

결과는 다음과 같았습니다.

확인 대상 관측 결과
Outbox 1행
Kafka record 같은 이벤트가 서로 다른 offset에 2건
consumer 수신 2회
구매 완료 receipt 1행
구매 활동 상품별 2행, 수량 2개와 1개 유지
PG 결제 생성 1회
최종 Outbox 상태 PUBLISHED

이벤트 하나에 상품 두 종류가 포함되어 있었으므로, 구매 활동의 기대 결과는 한 행이 아니라 상품별 두 행이었습니다. 재발행 이후에도 행 수와 각 상품의 수량이 늘어나지 않는지 확인했습니다.

6주차에는 offset을 커밋하지 않아 같은 record를 다시 읽는 상황을 실험했습니다. 이번에는 Kafka에 record 자체가 두 개 남았다는 점이 달랐습니다. 두 경우 모두 consumer에서는 같은 구매 사실을 추가로 반영하지 않아야 했습니다.

다만 이번 중단은 정해진 위치에서 발생시킨 예외였습니다. 프로세스를 강제 종료하거나 실제 네트워크에서 ACK만 유실시킨 실험까지 수행한 것은 아닙니다.

여기까지는 저장된 내용이 올바르다는 전제에서, 같은 내용을 다시 전달하는 문제였습니다.

4. 수량 20개를 한 번만 반영했다면

제가 질문드린 상황은 그 전제부터 달랐습니다.

실제 확정 주문 수량: 2개
Outbox에 저장된 수량: 20개
consumer에 반영된 수량: 20개

이 경우 consumer가 중복을 완벽하게 막더라도 결과는 잘못되어 있습니다. 20개를 두 번 반영하지 않았다는 사실이, 20개라는 수량까지 올바르다는 의미는 아니기 때문입니다.

이번 consumer는 전달받은 주문 확정 내용을 기준으로 구매 활동을 저장합니다. 원래 주문 DB를 다시 조회해서 수량이 맞는지 확인하지는 않습니다. producer가 20개를 정상적인 이벤트 형태로 전달하면, 첫 처리에서 그 내용으로 저장할 수 있습니다.

이후 Outbox의 수량을 2개로 바꾸어 다시 보내면 문제가 더 복잡해집니다.

처음 받은 이벤트
  eventId=A, orderId=1, quantity=20

수정 후 받은 이벤트
  eventId=A, orderId=1, quantity=2

현재 consumer는 같은 주문에 대해 저장한 내용과 새로 받은 내용을 비교합니다. 수량이나 최초 확정 시각 등이 다르면 같은 사실의 재전달로 보지 않고 충돌로 처리합니다.

그렇다면 eventId를 새로 만들면 되지 않을까...생각할 수도 있습니다. 하지만 현재 구현은 주문별 내용도 비교하므로, 새로운 eventId를 사용하더라도 같은 주문의 수량이 달라졌다면 충돌합니다.

새 식별자를 만드는 것만으로 정정의 의미가 생기지는 않았습니다. 기존 20개를 어떻게 처리하고, 새로 받은 2개를 어떤 업무로 해석할지부터 정해야 했습니다.

충돌을 거절하도록 한 것은 이런 불일치를 조용히 넘기지 않기 위한 장치였습니다. 다만 거절할 수 있다는 것과, 올바른 결과로 복구할 수 있다는 것은 별도의 문제였습니다.

5. 멘토님의 답변에서 다시 생각한 점

답변에서는 consumer를 먼저 멈추고, 문제가 있는 코드를 되돌리거나 수정한 뒤, 영향을 받은 데이터를 전수 확인하는 방향을 말씀해주셨습니다. 결제 취소와 재고 복구, 결제·상품·재고 대사, 고객 안내까지 언급하셨습니다.

Outbox도 수정해야 할 수 있으며, Outbox를 이벤트 소싱의 저장소처럼 생각할 필요는 없다는 말씀도 주셨습니다. 감사용 자료가 필요했다면 그 목적에 맞는 데이터를 따로 남겼어야 한다는 내용이었습니다.

저는 질문할 때 같은 eventId의 내용을 수정해도 되는지에 많이 집중했습니다. 그런데 답변을 듣고 보니, 이미 잘못된 내용으로 업무가 진행되고 있다면 먼저 더 퍼지지 않도록 멈추고 실제 영향을 확인해야겠다는 생각이 들었습니다.

예를 들어 구매 활동만 20개로 잘못 저장된 것인지, 결제 금액이나 재고까지 잘못 반영된 것인지에 따라 복구 범위가 달라질 것입니다. 어떤 상황에서도 전량 결제를 취소해야 한다는 뜻으로 이해하기보다는, 이벤트 한 건의 수정으로 끝나지 않는 장애가 될 수 있다는 말씀으로 받아들였습니다.

코드를 롤백해도 이미 저장된 구매 활동이 자동으로 2개가 되지는 않습니다. Outbox를 수정해도 Kafka에 남은 기존 record나 consumer가 처리한 결과까지 함께 변경되지는 않습니다.

잘못된 데이터를 더 만들지 않도록 하는 조치와, 이미 만들어진 데이터를 맞추는 조치를 함께 생각해야 했습니다.

Outbox를 수정하지 않는 이유도 목적에 따라 달랐습니다

이번 구현에서 payload를 변경하지 않도록 한 이유는 재시도할 때 같은 사건을 같은 내용으로 보내기 위해서였습니다. 그 선택을 하면서 Outbox를 모든 변경 이력을 영구히 보존하는 저장소로 설계한 것은 아니었습니다.

이벤트 소싱에서는 이벤트 기록을 기준으로 상태를 재구성합니다. 이때 원본 이벤트를 보존하고 정정하는 이벤트를 추가하는 것은 과거 상태와 변경 이유를 유지하는 데 중요한 의미가 있습니다. Microsoft Event Sourcing pattern

현재 과제에서는 주문 DB에 확정 사실이 있고, Outbox는 그 사실을 전달하기 위한 데이터를 저장합니다. 이벤트를 저장한다는 공통점은 있지만, 두 저장소가 맡은 역할까지 같지는 않았습니다.

그래서 발행되지 않은 것이 확실한 데이터까지 어떤 상황에서도 수정할 수 없다고 생각할 필요는 없겠다고 이해했습니다. 다만 수정할 수 있다는 것과, 수정한 뒤 다시 보내기만 하면 안전하다는 것은 구분해야 할 것 같습니다.

장애 당시 무엇이 잘못 저장되었고 어떤 근거로 수정했는지 남겨야 한다면, 그 기록도 별도로 필요할 것입니다. 현재 Outbox를 자동 삭제하지 않는다는 이유만으로 감사 기록까지 갖추었다고 볼 수는 없었습니다.

6. 발행 여부에 따라 무엇을 확인해야 할까

답변을 바탕으로 제가 생각한 확인 사항은 다음과 같습니다. 현재 구현한 자동 복구 절차가 아니라, 잘못된 payload를 정정하려면 추가로 검토해야 할 내용입니다.

확인한 상황 정정 전에 확인할 내용
발행되지 않은 것이 확실함 relay의 진행 중인 전송까지 없으며, 원본 주문을 근거로 잘못된 내용을 바로잡을 수 있는지
timeout 등으로 발행 여부를 모름 Kafka 기록과 consumer 처리 결과를 확인하고, 기존 내용이 뒤늦게 처리될 가능성까지 다룰 수 있는지
Kafka 발행이 확인됨 아직 처리하지 않은 consumer와 이미 처리한 consumer 각각에 어떤 조치가 필요한지
consumer의 업무 반영이 확인됨 잘못된 결과와 중복 확인 기록, 다른 후속 업무까지 함께 정정할 수 있는지

여기서 첫 번째 상황을 PENDING 상태와 같다고 보면 안될 것 같습니다. 앞의 실험에서도 Kafka에는 이벤트가 있었지만 Outbox는 PENDING이었습니다. relay를 멈추더라도 이미 진행 중이던 전송이 있는지 확인해야 할 것입니다.

발행되지 않은 것이 확실하다면 Outbox 내용을 수정하는 방향을 검토할 수 있습니다. 하지만 발행 여부가 불확실하다면 기존 20개와 수정된 2개가 모두 전달될 가능성을 생각해야 합니다.

수정된 2개가 먼저 처리되어도, 이후 기존 20개가 도착하면 현재 consumer는 충돌하게 됩니다. 반대 순서라면 잘못된 20개가 먼저 저장될 수 있습니다. 어느 쪽이 먼저 도착하기를 기대하는 방식으로는 복구하기 어려울 것 같습니다.

이미 업무 결과가 반영되었다면 Outbox뿐 아니라 consumer가 보관한 내용도 함께 확인해야 합니다. 현재 구현에서는 구매 활동만 2개로 수정하고 receipt의 비교 기준을 20개로 남겨두어도 서로 맞지 않는 상태가 됩니다.

그렇다고 receipt를 삭제한 뒤 다시 보내면 된다고 단정하기도 어렵습니다. 기존 구매 활동이 남아있거나, 과거 record가 다시 전달되면서 결과가 중복될 수 있기 때문입니다.

멘토님의 답변을 제 구현에 적용해보면, 우선 영향을 받는 처리 흐름을 멈추고 장애 구간의 원본 주문과 전달 데이터, 업무 결과를 대조하는 과정이 필요할 것 같습니다. 그 결과를 바탕으로 정정 방법과 재처리 범위를 정하고, 다시 실행한 뒤에도 수량과 관련 상태가 맞는지 확인해야 할 것입니다.

별도 정정 이벤트를 도입하는 방법도 생각할 수 있지만, 현재 consumer는 그 의미를 처리하도록 구현되어 있지 않습니다. 새 이벤트를 추가한다면 정정 대상과 순서, 중복 정정까지 계약으로 정해야 하므로, 이번에는 자동 정정 기능까지 확장하지 않았습니다.

7. 이번 실습에서 복구한 것과 남아있는 것

이번에 실제로 검증한 복구는 잘못된 수량을 고치는 작업과는 다릅니다. 6주차 구조에서 올바른 주문 확정 사실은 저장되었지만, 이벤트가 전달되지 않은 상황을 재현하고 복구했습니다.

실제 6주차 revision을 실행하여 두 주문을 준비했습니다.

주문 A
  주문 확정 성공
  Kafka 전송 직전에 실행 중단
  구매 활동 없음

주문 B
  주문 확정 성공
  Kafka 발행 및 구매 활동 저장 완료

그 뒤 같은 DB와 Kafka, PG 상태를 유지한 채 7주차 구현으로 연결했습니다. 대상 주문의 확정 사실을 검증하고, 없는 Outbox를 추가하여 발행했습니다.

주문 A에는 누락된 구매 활동이 생성되었고, 주문 B는 다시 전달되어도 기존 활동이 늘어나지 않았습니다. 복구를 두 번째 실행해도 결과가 추가로 변경되지 않는지 확인했습니다. 복구 과정에서 PG 결제 생성과 조회 호출도 증가하지 않았습니다.

이 실험은 새 테스트 실행에서 6주차의 상태를 재현한 것입니다. 과거 운영 DB를 복원한 실험은 아니며, 잘못된 payload와 이미 반영된 업무 결과를 정정하는 절차까지 검증한 것도 아닙니다.

7주차 검증 기록에서는 전체 223건이 실패와 skip 없이 통과했고, 관련 ktlintCheck와 ArchitectureTest도 통과했습니다. 다만 테스트를 통과한 범위는 주문 확정과 Outbox 저장의 원자성, 재발행, 소비 중복 방지, 명시한 누락 주문 복구입니다.

수량 2개가 20개로 저장된 상황은 이번 질문을 통해 추가로 생각하게 된 장애였습니다. 현재 구현이 충돌을 발견할 수는 있지만, 그 충돌을 정정하고 처리를 재개하는 기능까지 갖춘 것은 아닙니다.

짧은 회고

5주차에는 PG의 응답을 받지 못했을 때, 외부에 어떤 결과가 남았는지 다시 확인할 근거를 고민했습니다. 6주차에는 consumer가 중복을 막더라도, 전달되지 않은 이벤트는 별도로 찾아야 한다는 점을 생각했습니다. 이번에는 Outbox로 발행할 대상을 남기고 다시 보낼 수 있게 만들었습니다.

그런데 다시 보낼 수 있게 되니, 이번에는 저장한 내용 자체가 잘못되었을 때의 문제가 남았습니다. 수량 20개를 빠짐없이 전달하고 한 번만 반영해도, 실제 주문이 2개라면 업무 결과는 틀린 상태였습니다.

특히 같은 이벤트의 내용을 유지해야 한다는 구현 원칙을 생각하다 보니, 장애 상황에서도 원본을 절대 수정하면 안되는 것인지에 질문이 집중되었던 것 같습니다. 멘토님의 답변을 듣고 나서는 Outbox가 어떤 목적으로 존재하는지, 실제로 잘못된 결과가 어디까지 반영되었는지를 먼저 봐야겠다는 생각이 들었습니다.

아직 실무에서 어느 범위까지 중단하고, 어떤 데이터를 근거로 정정한 뒤 재개하는지는 더 경험해봐야 할 것 같습니다. 다만 이번에는 재시도가 가능하다는 설명에서 한 번 더 들어가, 무엇을 다시 보내는 것인지와 그 내용이 올바른지는 어떻게 확인할 것인지까지 고민하게 되었습니다.

Outbox를 적용하면서 발행 누락을 복구할 근거는 남길 수 있었습니다. 그 근거부터 잘못되었을 때는 전달 상태뿐 아니라 원본과 업무 결과를 함께 확인해야 한다는 점이 이번 주에 가장 남았습니다.

멘토님의 과제

  • CPU가 100%면 실행을 기다리는 작업이 늘면서 전체적으로 느려짐. 서버라면 응답이 늦어지고 타임아웃이 발생할 수 있음. CPU가 꽉 찼다는 이유만으로 프로세스가 바로 종료되지는 않지만, 헬스 체크에 응답하지 못해서 재시작될 수는 있음. 빌드나 인코딩 중이라면 정상적인 상태일 수도 있음.

  • 디스크 용량이 100%면 데이터를 추가로 저장하지 못해서 문제가 생김. 파일 저장, 로그 기록, 업로드, DB 쓰기 등이 실패할 수 있고, 저장 중이던 파일은 일부만 기록될 수도 있음. Linux에서는 ENOSPC 오류가 발생할 수 있음. 기존 파일을 읽는 건 가능해도, 서비스 내부에서 쓰기가 필요하면 조회 기능까지 영향을 받을 수 있음.

  • 디스크 I/O가 처리 한계에 걸리면 공간은 남아 있어도 읽기·쓰기가 밀리면서 느려짐. DB 쿼리나 파일 접근이 늦어지고, 심하면 타임아웃이 발생함. 이때는 CPU 사용률이 낮아도 서버가 느릴 수 있음. 다만 SSD는 I/O 사용률 100%만으로 성능 한계라고 단정하기 어려워서 지연시간도 같이 봐야 함.

  • 메모리가 실제로 부족해지면 캐시를 회수하거나 GC·스왑을 사용하면서 느려질 수 있음. 그래도 필요한 메모리를 확보하지 못하면 할당 오류가 나거나, OOM Killer가 프로세스를 강제 종료할 수 있음. 강제 종료되면 처리 중인 요청과 메모리에만 있던 데이터가 날아갈 수 있고, 재시작을 반복할 수도 있음. 서버 RAM이 남아 있어도 컨테이너나 프로그램의 메모리 한도 때문에 OOM이 발생할 수 있음. 반대로 캐시 때문에 사용률이 높은 건 정상일 수도 있음.

서로 영향을 주기도 함. CPU가 부족해서 요청이 쌓이면 메모리 사용량이 늘고, 메모리가 부족해서 스왑이 늘면 디스크 I/O까지 밀릴 수 있음. 그래서 사용률만 보는 게 아니라 응답 지연, 쓰기 실패, OOM 기록, 재시작 여부까지 같이 확인해야 함.
