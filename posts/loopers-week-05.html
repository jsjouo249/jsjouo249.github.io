PG는 결제했는데 우리 서버는 모른다면

1. 상황과 고민

이번 과제에서는 기존 포인트 결제를 외부 PG 결제로 변경하였습니다. 이전에는 주문과 포인트, 재고의 변경을 하나의 DB 트랜잭션 안에서 처리했지만, PG가 추가되면서 우리 DB의 상태와 외부 결제의 결과를 함께 생각해야 했습니다.

멘토링에서는 PG 웹훅의 재전송이 모두 유실되면 어떻게 정합성을 확인하는지 질문드렸습니다. 웹훅과 함께 조회 배치나 스케줄링, 일일 대사를 사용하는 방향에 대한 답변을 받았습니다. 여기서 대사는 우리 결제 데이터와 PG의 거래 내역을 비교하여 누락이나 불일치를 찾는 작업으로 이해했습니다.

결제 서버가 별도로 있는 구조에 대해서도 질문드렸습니다. 보내는 서버나 결제 서버가 멈춰 요청이 전달되지 않은 경우와, PG에서는 거래를 처리했지만 응답을 잃은 경우가 모두 REQUESTED로 남는다면 어떻게 구분해야 할지 궁금했습니다. 서버별로 진행 상태를 구분하는 방향을 들었지만, 한 가지 의문이 남았습니다.

결제 서버에서 PG로 요청을 보낸 뒤 상태를 변경하기 전에 서버가 죽으면...결국 기존 상태로 남는 것은 같지 않을까 싶었습니다. 그렇다고 외부 HTTP 호출까지 DB 트랜잭션으로 묶어서 해결할 수 있는 것도 아니었고, 배치를 돌리는 것에 대해서도 의문이 있었습니다.

이번에는 이 질문을 출발점으로, 로컬에 저장한 상태로 무엇을 알 수 있고 무엇은 다시 확인해야 하는지 정리해보려고 합니다. 현재 과제 구현은 별도 결제 서버를 두지 않고 application에서 PG를 호출하지만, 외부 요청과 DB 저장 사이의 고민은 그대로 남아있었습니다.

2. 상태를 나누면 어디까지 알 수 있을까

처음에는 PG로 요청을 보내는 단계를 SENDING이나 ONGOING으로 구분하면, 요청을 보내기 전과 후를 알 수 있을 것 같았습니다. 하지만 상태를 언제 저장할지 생각해보니 다음 두 경우가 남았습니다.

처리 순서 서버가 멈춘 시점 남는 상황
ONGOING 저장 후 PG 호출 상태 저장 직후, 호출 전 우리 DB는 진행 중이지만 PG 거래는 없음
PG 호출 후 ONGOING 저장 PG 처리 후, 상태 저장 전 우리 DB는 REQUESTED이지만 PG 거래는 있을 수 있음

상태를 구분하면 우리 서버가 어느 단계까지 기록했는지 설명하기는 쉬워집니다. 다만 그 상태만으로 외부에서 실제 거래가 생성되었는지까지 증명할 수 있는 것은 아니었습니다.

특히 timeout이 발생했다는 것은 우리 서버가 정해진 시간 안에 응답을 받지 못했다는 의미입니다. PG가 요청을 받지 못했는지, 처리 중인지, 이미 처리했지만 응답만 전달되지 않았는지는 별도로 확인해야 합니다. Stripe의 오류 처리 문서에서도 네트워크 연결이 복구되었다는 사실만으로 원래 요청의 성공 여부를 알 수는 없다고 설명합니다. Stripe Advanced error handling

그래서 REQUESTED가 오래 남아있다는 이유만으로 결제 실패로 바꾸거나, 같은 결제를 새로 요청하는 것은 조심해야겠다고 생각했습니다. 아직 알지 못하는 상태를 실패한 상태와 구분하는 것이 먼저였습니다.

3. 트랜잭션으로 묶으면 해결될까

우리 DB의 변경은 트랜잭션이 실패하면 롤백할 수 있습니다. 하지만 일반적인 DB 트랜잭션 안에서 PG를 호출한다고 해서, PG가 처리한 결제까지 같은 롤백에 참여하는 것은 아닙니다.

1. 우리 DB 트랜잭션 시작
2. PG 결제 성공
3. 우리 DB에 결과 저장 실패
4. 우리 DB 롤백
5. PG에는 성공한 결제가 남음

이 경우 우리 DB를 롤백한 것과 PG 결제를 되돌린 것은 다른 일입니다. PG가 처리하는 동안 DB 트랜잭션과 잠금을 오래 유지하는 비용까지 생깁니다.

그래서 이번 구현에서는 로컬 변경과 PG 호출을 다음과 같이 나누었습니다.

TX A
  주문과 재고 확인
  가용 재고 차감 및 예약 기록 저장
  결제 시도와 PAYMENT_PENDING 저장
  커밋

트랜잭션 밖
  TX A에서 새 시도를 생성하고 커밋 성공을 확인한 실행만 PG 생성 요청을 최대 1회 시도

TX B
  확인한 PG 결과 반영
  주문과 결제 시도, 재고 예약 상태 변경
  커밋

여기서 최대 1회는 반드시 한 번 전달된다는 보장은 아닙니다. TX A가 커밋된 직후 PG 호출 전에 프로세스가 종료되면 실제 생성 요청은 0회일 수 있고, 다시 요청하더라도 재발송하지 않습니다.

이렇게 나눈다고 두 시스템의 변경이 한 번에 성공하는 것은 아닙니다. 대신 외부 결제의 결과와 로컬 반영의 성공 여부를 구분했습니다. 로컬 결과 반영에 실패하면 TX B를 롤백하고 예외를 반환합니다. 이후 명시적인 reconcile 요청이나 PG callback 처리에서 기존 거래를 조회하고 결과 반영을 다시 시도합니다. 이 과정에서 PG 생성 요청은 재발송하지 않으며, 주기적인 자동 대사 스케줄러는 구현하지 않았습니다.

4. 이번 구현에서 미확정 결제를 다룬 방법

PG 요청 전에 조회할 식별자를 남겼습니다

결제 시도를 만들 때 주문과 연결된 providerOrderId를 먼저 저장합니다. PG가 반환하는 transactionKey는 응답을 잃으면 받지 못할 수도 있으므로, PG 응답으로 얻는 키에만 의존하지 않도록 했습니다. 현재 연동에서는 미리 정한 providerOrderId로 PG 거래를 조회할 수 있습니다.

결제 시도의 상태는 다음과 같이 구분했습니다.

상태 이번 구현에서의 의미
REQUESTED PG 호출을 시도하기 위한 로컬 기록이 저장됨. 실제 전달 여부까지 보장하지는 않음
PENDING PG 조회 또는 응답에서 처리 중인 거래가 확인됨
UNKNOWN 응답 유실이나 조회 불가 등으로 결제 결과를 확정하지 못함
SUCCESS 검증한 PG 성공 결과를 반영함
FAILED 검증한 실패 결과 또는 거래 생성 전 무효과 거절을 반영함

모르는 상태에서 결제를 다시 생성하지 않았습니다

동일한 결제 시도로 다시 요청하더라도 기존 시도를 반환하고, PG 생성 요청을 자동으로 다시 보내지 않도록 했습니다. 응답을 잃었을 때 실패로 단정하여 재요청하면, 이미 만들어진 거래에 더해 다른 거래가 생길 수 있기 때문입니다.

여기서 우리 DB의 paymentAttemptKey 중복을 막는 것과 PG가 멱등성을 보장하는 것은 구분해야 했습니다. 우리 DB에서 같은 요청을 알아볼 수 있다고 해서, PG도 반복 요청을 같은 결제로 처리해주는 것은 아닙니다.

예를 들어 Stripe는 정해진 보장 범위 안에서 같은 멱등키와 같은 요청 내용으로 재시도하는 방법을 제공합니다. 하지만 이것을 모든 PG와 모든 API의 동작으로 가정할 수는 없고, 키의 유효기간과 오류 처리 계약까지 확인해야 합니다. Stripe Advanced error handling

확인한 결과를 같은 경계에서 반영했습니다

이번 구현의 callback은 결제 성공을 직접 확정하는 입력으로 사용하지 않았습니다. callback으로 전달된 식별자를 바탕으로 PG를 조회한 뒤, 계정과 주문 식별자, 금액, 거래 키를 확인하고 결과를 반영합니다. 수동 reconcile도 같은 결과 반영 경계를 사용합니다.

성공이면 예약된 재고를 소비하고 주문을 확정합니다. 가용 재고는 TX A의 예약 시점에 이미 차감했으므로, 결제 성공 때 추가로 차감하지 않습니다. 실패가 확인되면 예약을 해제하고 재고를 반환합니다. timeout이나 조회 결과 0건, 404만으로는 예약을 해제하지 않습니다.

중복 callback이나 조회가 겹쳐도 재고가 두 번 반환되거나, 이미 성공한 결제가 뒤늦은 PENDING 응답으로 돌아가지 않도록 했습니다. 결과를 다시 확인하는 것과 업무 효과를 다시 적용하는 것은 다르게 처리해야 했습니다.

5. 장애를 테스트한다면 무엇을 확인해야 할까

정상적으로 결제되는지만 확인해서는 처음의 질문에 답하기 어려웠습니다. 외부 거래가 남는 시점과 로컬에 결과를 저장하는 시점 사이에 실패를 넣고, 양쪽 상태를 함께 봐야 합니다.

현재 테스트에는 아래 조건과 기대 상태를 작성해두었습니다. 최종 DB 통합 검증은 아직 완료하지 못했으므로, 아래 표는 전체 실험이 통과했다는 결과가 아니라 테스트가 검증하려는 내용입니다.

재현 조건 PG 쪽에서 확인할 것 로컬에서 확인할 것
발송 기록 저장 후 HTTP 호출 전 예외 생성 요청 0회, 거래 없음 예약 유지. 새 서비스 인스턴스에서도 재전송하지 않음
PG 거래 생성 후 응답 연결 종료 생성 요청 1회, 거래 1건 UNKNOWN과 예약 유지. 이후 같은 거래 조회로 종결
PG 성공 결과의 로컬 반영 중 예외 기존 성공 거래 유지 주문과 예약 변경 롤백. 다시 조회하면 결과 반영

응답 유실을 다루는 HTTP fixture는 거래를 메모리에 저장한 뒤 응답 연결을 닫도록 구성했습니다. 실제로 HTTP 요청을 보내지만 정상 응답을 받지 못하게 하여, 외부 거래가 있다는 사실과 로컬에서 결과를 모르는 상황을 함께 만들려는 것입니다.

호출 전 중단 테스트는 예외를 발생시키고 새 서비스 인스턴스를 만드는 방식입니다. 실제 프로세스를 종료하고 재시작하는 실험과는 구분해야 합니다.

처음 질문했던 상황을 더 직접적으로 확인하려면, PG에 성공 거래를 남긴 직후 로컬 결과 반영 전에 중단하는 조건도 추가하고 싶습니다. 이때 조회 전에는 로컬 REQUESTED와 외부 성공 거래가 함께 남는지, 조회 후에는 같은 거래로 주문이 확정되는지 확인할 수 있을 것 같습니다.

이 과정에서 중요한 것은 예외가 발생했다는 사실만 확인하는 것이 아니었습니다. 생성 요청 횟수와 PG 거래 수, 주문 상태와 재고 예약 상태까지 함께 봐야 중복 결제를 막았는지, 복구가 가능한지 설명할 수 있습니다.

6. 웹훅 대신 계속 조회하면 되는 걸까

사전에 저장한 식별자로 PG를 조회하면 된다고 생각하니, 다시 궁금한 점이 생겼습니다. 그렇다면 웹훅을 믿기보다 계속 조회하는 것이 가장 확실한 방법일까...싶었습니다. 하지만 조회 요청도 실패할 수 있고, PG가 전체적으로 응답하지 않는다면 같은 곳을 계속 호출하는 것만으로 해결되지는 않을 것입니다.

웹훅과 조회를 서로 대체하는 방법으로만 생각할 필요는 없을 것 같습니다. 웹훅으로 결과를 빠르게 받고, 일정 시간 동안 끝나지 않은 결제는 조회로 확인하며, 거래 내역을 비교하는 대사를 통해 누락을 찾는 식으로 역할을 나눌 수 있습니다.

모든 웹훅을 받은 뒤 반드시 다시 조회해야 한다는 일반 규칙이 있는 것도 아닙니다. 이번 과제는 callback을 조회의 계기로 사용했지만, 실제 PG의 서명 검증 방식과 이벤트 계약에 따라 처리 방법을 정해야 합니다. Stripe는 웹훅으로 비동기 결제 결과를 처리하도록 안내하며, 반복 조회로 대체할 때에는 신뢰성과 호출 제한 문제를 주의하라고 설명합니다. Stripe Payment status updates

자동 복구를 추가한다면, 조회가 실패한 결제를 다시 찾을 수 있도록 미완료 상태와 다음 확인 시각을 DB에 남기는 방향을 생각하고 있습니다. 조회 간격은 점차 늘리고, 확인되지 않은 기간이 길어지면 알림이나 수동 대사로 연결하는 방식입니다. 현재 과제에는 이 스케줄러와 일일 대사를 구현하지 않았고, 수동 reconcile이 기본 복구 경로입니다.

트래픽이 적다는 이유로 조회 주기를 길게 잡아도 되는지도 다시 생각하게 되었습니다. 결제 후 이어지는 업무가 있다면, 건수가 적어도 한 사용자는 계속 기다리고 있을 수 있습니다. 조회 비용뿐 아니라 사용자가 기다릴 수 있는 시간과 PG의 호출 제한을 함께 보고 기준을 잡아야 할 것 같습니다.

조회를 담당하는 서버도 죽으면 어떻게 될까

조회할 대상을 DB에 남기고 다른 워커가 이어서 처리할 수 있게 하면, 특정 워커가 죽어서 복구가 멈추는 문제는 줄일 수 있습니다. 하지만 이미 요청을 받은 PG와 통신할 수 없는 동안에는 그 거래의 결과를 즉시 확인할 수 없습니다. 다른 PG를 추가하더라도 기존 PG가 처리한 거래의 결과까지 대신 알려주지는 못합니다.

PG가 복구되고 거래 기록을 조회할 수 있다는 조건이 있어야 이후의 복구도 가능합니다. 장애 중에도 즉시 결과를 아는 것과, 장애가 풀린 뒤 확인을 이어갈 수 있는 것은 다른 보장이라는 생각이 들었습니다.

7. outbox를 사용했다면 달라졌을까

이번 5주차에는 transactional outbox를 사용하지 않았습니다. 다만 요청을 보내기 전에 서버가 멈추는 문제를 보면서, DB 변경과 전달할 메시지를 같은 트랜잭션에 저장하는 방식도 떠올리게 되었습니다.

outbox는 커밋된 변경에 대해 나중에 메시지 전달을 다시 시도할 근거를 남길 수 있습니다. 하지만 전달 후 완료 기록 전에 중단되면 같은 메시지를 다시 보낼 수 있어, 받는 쪽에서도 중복을 처리할 수 있어야 합니다. GCP의 Pub/Sub도 기본 전달 방식이 최소 한 번(at-least-once)이므로, 같은 메시지가 여러 번 전달될 수 있고 구독자의 멱등 처리가 필요하다고 설명합니다. GCP Pub/Sub Subscription overview

결제 요청 전달에 적용하더라도 PG의 멱등성 계약과 결과 확인 방법은 여전히 필요합니다. PG가 처리한 뒤 로컬 기록 전에 멈추는 구간까지 outbox 하나로 없앨 수 있는 것은 아니기 때문입니다.

그래서 지금은 특정 패턴을 추가할지보다, 어떤 요청을 안전하게 반복할 수 있고 결과를 어떤 식별자로 확인할 수 있는지부터 정리하는 것이 우선이라고 생각했습니다.

짧은 회고

4주차에는 캐시에 revision을 넣지 않기로 한 뒤, 그 선택으로 어느 정도의 신선도까지 보장할 수 있는지 고민했습니다. 이번에는 결제 상태를 나누고 조회 경로를 추가하면 정합성을 맞출 수 있을 것 같았지만, 상태만으로는 외부에서 일어난 일을 모두 알 수 없다는 점을 생각하게 되었습니다.

특히 이번 구현에서 남은 비용은 분명했습니다. 중복 결제를 막기 위해 자동 재전송을 금지했지만, 실제로 PG에 보내지 못한 요청도 미완료로 남을 수 있습니다. 이 경우 조회만으로는 결제를 진행시킬 수 없고, 예약한 재고도 계속 점유하게 됩니다. 이 선택이 실제 서비스에서도 충분한지는 사용자가 기다리는 시간과 운영자가 확인하는 비용까지 함께 봐야 할 것 같습니다.

처음에는 성공과 실패를 어떻게 나눌지에 집중했는데, 외부 시스템이 들어오니 아직 결과를 모르는 상태를 다루는 일이 중요해졌습니다. 실패로 확정할 수 없는 상태에서 어떤 변경을 멈춰야 하는지, 나중에 무엇을 근거로 다시 판단할지까지 정해야 했습니다.

모든 장애를 없애지는 못하더라도, 확인할 결제를 잃지 않고 확인된 결과를 중복 적용하지 않도록 만드는 것이 이번 과제에서 가져가고 싶은 기준입니다.
