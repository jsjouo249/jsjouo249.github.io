쿠폰 발급의 원본을 DB에서 Redis로 옮겨보니

1. 상황과 고민

이번 과제에서는 Redis 세마포어로 동시에 진행되는 쿠폰 발급 수를 제한했습니다. 원래 발제의 흐름은 세마포어로 진입을 제한하고, DB 트랜잭션에서 중복과 발급 한도를 확인한 뒤 쿠폰을 저장하는 것이었습니다. 세마포어 자리가 가득 차면 대기하지 않고 바로 실패하는 조건이었습니다.

구현을 하면서 Lua로 중복 확인과 한도 검사부터 발급 결과 기록까지 한 곳에서 처리해보고 싶었습니다. Redis를 발급의 SSOT로 두고, DB에는 그 결과를 나중에 반영하면 어떨까...생각했습니다. 여기서 SSOT(Single Source of Truth)는 쿠폰 발급이 확정되었는지 판단하는 기준 기록을 뜻합니다.

처음 떠올린 흐름은 Redis에서 발급하고, 그 결과를 DB에 비동기로 저장하는 정도였습니다. 그런데 Redis의 기록을 발급 성공으로 본다면, DB에 아직 없는 쿠폰도 사용자에게는 이미 발급된 쿠폰이 됩니다. 그 쿠폰을 어디에서 조회하고, 기록 도중 오류가 나면 무엇을 믿어야 할지도 함께 정해야 했습니다.

특히 Lua로 여러 명령을 한 번에 실행할 수 있다는 것과, 도중에 실패해도 모든 변경을 되돌릴 수 있다는 것은 같은 이야기가 아니었습니다.

이번에는 Redis에 기록되면 발급에 성공한 것으로 보면서, 쿠폰 조회와 DB 반영이 실패했을 때는 어떻게 처리해야 할지 정리해보려고 합니다. 원래 과제와 다르게 세마포어 자리가 생길 때까지 최대 30초를 기다리도록 한 선택도 함께 돌아보았습니다.

2. Redis에 기록되면 발급 성공으로 보았습니다

먼저 발급 성공의 기준을 바꾸었습니다. DB commit을 기다리는 대신, Redis에 발급 사실과 이벤트를 기록한 뒤 신규 발급에 201을 응답하도록 했습니다. 같은 사용자와 캠페인의 기존 발급이 있다면, 처음 저장한 쿠폰을 그대로 읽어 같은 couponId로 200을 반환합니다.

현재 흐름은 다음과 같습니다.

DB에서 사용자 존재 확인
  → Redis에서 기존 발급 조회
      있으면 같은 쿠폰으로 200
      없으면 Redis 세마포어 획득
        → Lua에서 중복·한도 확인과 발급 기록
        → 자기 슬롯 반환 시도
        → 신규 201 또는 동시 중복 요청의 기존 결과 200

worker
  → Redis Stream 읽기
  → DB 트랜잭션으로 발급 결과 반영
  → commit 후 ACK

세마포어를 얻기 전에 기존 결과를 먼저 조회합니다. 이미 발급된 쿠폰을 확인하는 요청까지 새로운 발급 자리를 기다릴 필요는 없다고 생각했습니다. 두 요청이 동시에 기존 결과를 찾지 못한 경우에는 발급 Lua에서 다시 중복을 확인합니다.

이렇게 바꾸고 나니, 목록을 DB에서 읽는 것도 맞지 않았습니다. POST에서는 성공했다고 응답했는데 DB 반영이 늦어 GET에서는 쿠폰이 보이지 않을 수 있기 때문입니다. 그래서 보유 목록도 Redis primary에서 읽도록 했습니다.

판단할 내용 현재 기준
발급 한도와 사용자별 중복 Redis의 발급 기록
신규 발급 성공 Lua가 발급 사실과 Stream 기록을 마침
재요청과 보유 목록 Redis에 저장된 같은 쿠폰
DB의 쿠폰 데이터 Redis의 발급 사실을 나중에 반영한 결과

Redis를 읽지 못하면 목록도 503으로 응답합니다. 지연된 DB를 대신 읽으면, 현재 발급 결과를 모두 보여준다는 설명을 할 수 없기 때문입니다.

다만 DB에 전혀 접근하지 않는 구조가 된 것은 아닙니다. 요청한 사용자가 존재하는지 확인하는 기존 DB 조회는 유지했습니다. 발급을 확정하는 저장소를 바꾼 것이며, 전체 API가 DB 장애와 독립적으로 동작하도록 만든 것은 아닙니다.

3. Lua가 실패하면 앞의 쓰기는 어떻게 될까

Lua 안에서는 중복과 한도를 확인하고, 새 ID를 정한 뒤 발급 사실과 Stream을 기록합니다. 다른 발급 요청이 그 사이에 끼어들지 않으므로, 여러 요청이 같은 남은 수량을 보고 각각 발급하는 상황을 막을 수 있습니다. Redis 공식 문서에서도 스크립트가 실행되는 동안 다른 요청의 처리가 끼어들지 않는 원자적 실행을 설명합니다. Redis Scripting

다만...명령이 순서대로 실행된다는 설명만으로 오류 상황까지 이해했다고 보기는 어려웠습니다. 발급 수를 늘린 뒤 Stream에 기록하는 명령에서 실패하면, 앞의 변경도 함께 취소되는지 확인해보고 싶었습니다.

실험에서는 테스트 전용 Redis 사용자에게 다른 명령은 허용하고 XADD 권한만 막았습니다. 그리고 실제 발급 Lua를 실행했습니다.

확인한 대상 XADD 오류 이후 상태
캠페인의 발급 수 1로 증가한 상태
사용자의 보유 기록 쿠폰 기록이 남음
Stream 이벤트 수 0
원본 상태 DIRTY

발급 수와 보유 기록을 변경하는 명령은 실행되었지만, Stream에 기록하는 명령은 실패했습니다. 다른 요청이 중간에 끼어들지 않았어도, 오류 전에 실행한 쓰기는 남아있었습니다.

지난주에는 주문 확정과 Outbox 저장을 하나의 DB 트랜잭션으로 묶고, 저장 실패 시 로컬 변경이 함께 롤백되는지 확인했습니다. 이번에도 발급 사실과 전달할 이벤트를 함께 남기지만, 그때의 rollback을 Lua에도 그대로 기대할 수는 없었습니다.

부분 변경을 발견하면 먼저 멈추도록 했습니다

이 상태를 정상 발급처럼 읽거나 다음 발급을 이어가면 안 되겠다고 생각했습니다. 그래서 쓰기 전에 입력과 키 타입, TTL, 수량 등을 확인하고, 다음 ID 계산과 JSON 직렬화도 먼저 마치도록 했습니다.

그 뒤 실제 쓰기는 다음 순서로 실행합니다.

redis.call('HSET', meta, 'health', 'DIRTY')
redis.call('HSET', meta, 'sequence', nextId)
redis.call('HINCRBY', campaign, 'issued', 1)
redis.call('HINCRBY', meta, 'owner:' .. ARGV[1], 1)
redis.call('HSET', owner, ARGV[2], payload)
redis.call('XADD', events, '*', 'fact', payload)
redis.call('HSET', meta, 'health', 'READY')

여러 쓰기를 시작하기 전에 DIRTY를 남기고, 모두 마친 경우에만 READY로 바꿉니다. XADD에서 실패하면 마지막 READY 변경까지 도달하지 않으므로, DIRTY가 남은 원본은 조회·발급·worker에서 사용하지 않습니다. 실제 구현은 발급 Lua에 있습니다.

이 표식이 부분 변경을 복원해주는 것은 아닙니다. 어떤 기록이 남았는지 대조하기 전까지 더 진행하지 않게 하는 장치입니다. 세마포어를 다시 열더라도 발급 수와 쿠폰, Stream, DIRTY를 지우지 않도록 했습니다.

자동으로 수량을 줄여 되돌리는 방법도 쉽게 선택하기는 어려웠습니다. 어디까지 반영되었는지 알지 못한 채 보정하면, 남아있는 쿠폰 기록과 수량이 다시 어긋날 수 있기 때문입니다. 현재는 원본이 정상인지 확인할 수 없다면 처리를 멈춘 상태로 두고, 수동으로 확인하는 데까지 범위를 잡았습니다.

4. DB에는 같은 발급 사실을 다시 반영할 수 있게 했습니다

Redis에서 성공을 확정한다고 해서 DB 저장이 항상 성공하는 것은 아닙니다. worker가 이벤트를 읽은 뒤 DB 저장에 실패할 수도 있고, DB commit은 끝났지만 ACK에 실패할 수도 있습니다.

worker는 자기 consumer의 pending을 먼저 읽고, 없으면 새 이벤트를 읽습니다. DB에서는 캠페인을 잠그고 이미 같은 발급 사실이 저장되어 있는지 확인합니다. 새로운 사실이면 발급 수와 쿠폰을 같은 트랜잭션에서 반영하고, 이미 같은 ID·소유자·시각·혜택이 저장되어 있다면 다시 증가시키지 않습니다. 같은 식별자에 다른 내용이 들어오면 정상 재처리로 넘기지 않고 충돌로 처리합니다.

순서는 DB commit 이후 ACK로 잡았습니다.

DB 저장 실패
  → DB 트랜잭션 rollback
  → Redis의 발급 사실과 재처리할 이벤트는 유지

DB commit 성공, ACK 실패
  → 다음 실행에서 같은 이벤트를 다시 읽을 수 있음
  → 이미 반영한 같은 사실이면 추가 변경 없이 ACK

ACK를 먼저 하면 DB에 반영하지 않은 이벤트를 처리한 것으로 넘길 수 있습니다. 반대로 commit 이후 ACK를 하더라도, 두 작업 사이에서 멈추는 상황은 남습니다. 그래서 ACK 순서와 함께 DB 반영의 멱등성도 필요했습니다.

실제 MySQL 통합 테스트에서는 쿠폰 insert 실패로 DB 변경을 롤백해도 Redis의 발급 사실은 유지되는지 확인했습니다. commit 이후 ACK만 실패시킨 경우에도, 재처리 뒤 쿠폰 수와 발급 수가 두 번 증가하지 않았습니다.

여기서 DB 실패를 이유로 Redis에서 확정한 발급을 취소하지는 않습니다. 이번에 정한 성공 기준은 Redis이기 때문입니다. 다만 DB 장애가 계속되면 반영이 밀리며, 앞서 남겨둔 사용자 확인 DB 조회도 영향을 받을 수 있습니다.

5. 자리가 없으면 바로 실패시켜야 할까

발급 원본을 바꾸면서도 Redis 세마포어는 유지했습니다. 발급 한도와 동시에 진행할 실행 수는 서로 다른 문제라고 생각했습니다.

세마포어 용량이 3이라면, 현재 슬롯을 점유한 발급 실행은 3개로 제한할 수 있습니다. 하지만 실행이 끝나 슬롯이 반환되면 다음 요청도 들어갈 수 있으므로, 세마포어만으로 캠페인의 누적 발급 수까지 제한할 수는 없습니다. 누적 한도와 사용자별 중복은 발급 Lua에서 확인하도록 했습니다.

원래 과제에서는 세마포어 자리가 없으면 바로 실패합니다. 저는 잠깐 기다리는 동안 슬롯이 반환된다면, 같은 요청에서 발급을 이어가도 되지 않을까...생각했습니다. 그래서 슬롯을 얻을 때까지 최대 30초를 기다리도록 했습니다.

기다린다고 항상 발급할 수 있는 것은 아닙니다. 슬롯을 얻더라도 그사이에 쿠폰이 품절되었으면 발급 Lua에서 품절로 거절됩니다. 처리할 자리가 없다는 것과 발급할 쿠폰이 없다는 것은 구분해야 했습니다.

대기를 허용하면 기다리는 HTTP 요청과 Servlet thread도 늘어납니다. 그래서 한 앱에서 동시에 기다리는 요청은 최대 50개로 제한했습니다. 슬롯 반환 알림으로 대기자를 깨우고, 알림이 없더라도 200ms에 ±25% jitter를 준 간격으로 재검사하도록 했습니다. 대기 중에는 발급용 DB 트랜잭션을 열거나 Redis 활성 슬롯을 점유하지 않습니다.

기다리는 시간이 끝나거나 대기 요청 수의 상한을 넘으면 429로 반환합니다. 반면 Redis 명령에서 오류가 나거나 실행 결과를 확인할 수 없다면, 계속 기다리며 재시도하지 않고 503으로 처리합니다. Redis의 응답을 읽지 못한 것을 슬롯이 가득 찼다는 응답과 같게 볼 수는 없기 때문입니다.

여기서 30초는 슬롯 획득을 기다리는 한도입니다. 획득한 token을 자동 회수하는 TTL도 아니고, 이미 전송한 Redis 명령이나 전체 HTTP 처리를 정확히 30초 안에 끝내는 제한도 아닙니다. FIFO나 발급 순번 예약을 제공하는 대기실도 아닙니다.

실제 Redis 테스트에서는 세 슬롯을 점유한 동안 네 번째 요청이 기다리고, 슬롯 하나를 반환하면 같은 요청이 발급을 이어가는지 확인했습니다. 다만 즉시 실패하는 방식과 비교해 처리량이나 성공률이 얼마나 달라지는지는 측정하지 않았습니다. 대기 시간 30초와 대기 요청 50개가 실제 서비스의 적정값이라고 말하기보다는, 이번에 선택한 대기의 상한으로 설명하는 것이 맞을 것 같습니다.

실행 결과를 모르면 슬롯도 바로 돌려주지 않았습니다

Redis 명령이 timeout되면, 서버에서 실행되지 않은 것인지 실행은 되었지만 응답을 받지 못한 것인지 알기 어렵습니다. 이때 슬롯을 바로 반환하거나 TTL로 회수하면, 이전 실행이 끝나기 전에 다음 실행을 받을 수 있습니다.

그래서 실행 결과를 확인할 수 없다면 슬롯을 그대로 유지하고, 새로운 발급 요청은 받지 않도록 했습니다. 이미 Redis에서 발급이 확정된 경우에는 슬롯 반환 실패가 발급 취소로 이어지지 않게 했습니다. 기존 실행과 Redis 작업이 끝났는지 확인한 뒤 발급을 다시 시작하도록 했고, 자동으로 복구하는 기능까지 구현하지는 않았습니다.

새로운 발급 요청을 받지 않더라도, 기존 쿠폰을 확인하는 조회는 계속할 수 있도록 했습니다. Redis가 정상이고 원본이 READY 상태라면 기존 쿠폰과 보유 목록은 읽을 수 있습니다. 원본 자체에 DIRTY가 남아 조회·발급·worker를 모두 막는 경우와는 구분했습니다.

6. primary와 replica가 있으면 안심해도 될까

Redis를 발급 원본으로 정하고 나니, 이미 성공했다고 응답한 쿠폰이 장애 뒤에도 남는지가 더 걱정되었습니다.

저장소의 Compose 구성은 Redis primary 1개와 replica 1개입니다. AOF always와 noeviction을 전제로 하고, 발급을 준비하거나 다시 시작할 때 해당 설정도 확인합니다. 다만 클라이언트는 고정 주소로 연결하며 Sentinel이나 자동 failover는 없습니다.

primary의 AOF에 기록했다는 것과 replica에도 같은 내용이 영속화되었다는 것은 구분해야 했습니다. Redis 기본 복제는 비동기이며, primary가 매번 replica의 처리를 기다린 뒤 응답하는 구조는 아닙니다. Redis Replication

특히 이번에는 발급 사실과 DB로 전달할 Stream이 같은 Redis에 있습니다. replica 복제와 DB 반영 전에 둘이 함께 유실되면, DB에는 복원할 쿠폰 자체가 없을 수 있습니다. DB에 비동기로 저장한다는 사실만으로 이미 성공한 발급을 전부 복구할 수 있는 것은 아니었습니다.

DIRTY도 이 문제를 모두 찾아주지는 못합니다. 스크립트가 중간에 실패해 표식이 남은 경우는 차단하지만, 정상 완료한 변경 전체가 사라져 과거의 일관된 READY 상태로 돌아간 상황까지 모두 감지하지는 못합니다. 현재 READY는 Lua의 쓰기가 끝났다는 표식이며, replica 영속화 완료를 확인한 표식은 아닙니다.

성공 응답 전에 primary와 replica의 AOF 영속화를 확인하는 방향이나, 장애 전환 뒤 어느 데이터를 기준으로 재개할지 검토할 수 있을 것 같습니다. Redis 7.2부터 제공하는 WAITAOF도 검토 대상이지만, 공식 문서에서도 이 명령이 Redis를 강한 일관성 저장소로 만드는 것은 아니라고 설명합니다. WAITAOF 현재 Compose의 Redis 7.0에는 적용하지 않았습니다.

이 부분은 어떤 장애까지 견디려는지부터 정해야 할 것 같습니다. primary 한 대의 장애를 다룰 것인지, 두 저장장치의 손실까지 다룰 것인지에 따라 필요한 근거가 달라질 것입니다. 성공했다고 응답한 쿠폰이 유실되는 것을 어디까지 허용할지, 복구에는 얼마나 걸려도 괜찮을지, replica를 확인하지 못하면 발급을 멈출지도 함께 정해야 합니다.

이번에는 그 범위를 정하지 않은 채 HA 구성을 더 추가하지는 않았습니다. 로컬 발급 앱 한 대에서 문제가 생기면 새로운 발급 요청을 받지 않도록 멈추고, 수동으로 상태를 확인한 뒤 다시 발급을 시작하는 데까지 구현했습니다. Redis에 기록하는 것부터 복구까지 모두 해결했다는 설명은 할 수 없었습니다.

7. 실제로 확인한 범위

발급 경쟁과 중복뿐 아니라, 오류가 난 뒤 무엇이 남는지도 확인하려고 했습니다. Lua 본문을 mock으로 대체하지 않고 실제 Redis에서 실행했습니다.

실험 확인한 결과
획득한 슬롯을 유지한 60개 경쟁 세마포어 용량 3개만 획득
발급용 슬롯을 충분히 둔 8명·한도 5장 경쟁 발급 5건·품절 3건
같은 사용자의 동시 발급 같은 couponId와 하나의 생성 효과·이벤트
XADD 권한만 거절 선행 쓰기와 DIRTY가 남고 조회·발급·worker 차단
DB commit 이후 ACK 실패 재처리해도 쿠폰과 발급 수의 중복 증가 없음

키 타입이나 TTL이 예상과 다르거나, sequence에 문제가 생기면 어떻게 될지도 확인했습니다. Stream이나 consumer group이 사라지는 경우까지 포함해 20개 사례를 추가했습니다. 요청을 거절하기 전과 후의 원본과 Stream, 슬롯 점유 기록을 비교하면서, 실패한 요청이 데이터를 추가로 변경하지 않는지 확인했습니다.

Compose와 같은 Redis 7.0.15와 로컬 Redis 8.10.1에서 같은 Lua smoke를 실행했습니다. 위의 경쟁과 중복, 부분 오류, Stream 재전달·ACK, 정상 AOF 재시작을 두 버전에서 확인했습니다. 정상 재시작 실험은 프로세스 강제 종료나 실제 replica 승격, 네트워크 분할을 검증한 것은 아닙니다.

기존 기능 회귀를 포함한 최종 검증은 API 250건, W7 E2E 2건, 실제 JVM Redis 27건으로 총 279건이 실패·오류·skip 없이 통과했습니다. API의 ktlintCheck와 ArchitectureTest도 통과했습니다. 세부 실행 결과와 각 검사의 범위는 검증 기록에 정리했습니다.

짧은 회고

4주차에는 Redis에 상품 목록을 캐싱하면서, 어떤 데이터가 오래되어도 괜찮고 어떤 판단은 DB에서 해야 하는지 고민했습니다. 이번에는 쿠폰 발급 자체의 원본을 Redis로 옮겼습니다.

원본을 옮기는 결정은 저장하는 위치만 바꾸는 것보다 많은 부분에 영향을 주었습니다. 성공을 언제 응답할지, 성공한 쿠폰을 어디에서 읽을지, DB 반영이 실패하면 무엇을 유지할지까지 함께 바뀌었습니다. Lua에서 오류가 나기 전의 쓰기가 남는 것을 확인하면서, 발급을 계속해도 되는 상태인지 먼저 판단해야 한다는 점도 생각하게 되었습니다.

세마포어에 30초 대기를 추가한 것도 비슷했습니다. 바로 실패시키지 않기로 하니, 기다리는 요청이 사용하는 자원뿐 아니라 요청이 취소되거나 실행 결과를 확인할 수 없는 상황까지 함께 생각해야 했습니다.

아직 Redis를 발급 원본으로 사용하는 것이 실제 서비스에서도 적절한지까지 답하기는 어렵습니다. 실무에서는 성공한 쿠폰을 어디까지 보존해야 하는지, 어떤 상태를 확인한 뒤 발급을 다시 여는지가 더 궁금합니다.

다만 이번에는 Redis에 기록하면 끝나는 흐름을 만드는 데서 한 번 더 들어가, 그 기록을 어떤 근거로 성공이라고 설명할 수 있는지 고민해볼 수 있었습니다.
