루퍼스 3주차 기록: InnoDB에 대해

이름만 알았던 InnoDB를 공부하며, 인덱스와 트랜잭션, 잠금이 어떻게 연결되는지 정리합니다.

TAGS

#loopers #weekly #learning

이름만 알고 있던 InnoDB에 대해

  • 이번 주차의 주제는 동시성이었습니다.
  • 멘토님께서 Real MySQL 8.0을 읽어보라고 말씀해주셨고, 책을 읽다보니...MySQL을 사용하면서도 InnoDB 엔진에 대해서는 아는 것이 거의 없다는 생각이 들었습니다.
  • 마침 이번 주차에는 연휴도 있어서, 해당 부분을 조금 더 공부하게 되었습니다.
  • 그래서 이번에는 InnoDB에 대해 공부한 내용을 정리해보려고 합니다.
  • 처음엔 동시성과는 조금 다른 주제를 공부하는 것 같았지만, 인덱스와 트랜잭션, 잠금까지 읽고 나니 결국 동시성과 연결되는 내용이었다는 생각이 들었습니다.

MySQL 엔진과 스토리지 엔진

  • 우선 MySQL 서버는 크게 MySQL 엔진과 스토리지 엔진으로 나누어 볼 수 있습니다.
  • MySQL 엔진: 클라이언트의 접속과 쿼리 요청을 처리하고, SQL을 분석하여 실행 계획을 결정하는 부분
  • 스토리지 엔진: 실제 데이터를 디스크에 저장하거나 읽어오는 부분
  • MySQL 엔진에는 커넥션 핸들러와 SQL 파서, 전처리기, 옵티마이저 등이 있으며, SQL을 어떻게 실행할지 판단하는 역할을 합니다.
  • 스토리지 엔진은 그 실행 계획에 따라 실제 데이터를 읽고 쓰는 역할을 하고, 이번에 공부한 InnoDB가 여기에 해당합니다.
  • MySQL을 사용한다는 것만 생각했지, 내부에서 이렇게 역할이 나뉘어 있다는 것은 크게 생각해보지 않았던 것 같습니다.

InnoDB

  • InnoDB는 레코드 수준의 잠금과 트랜잭션을 지원하는 스토리지 엔진입니다.
  • 테이블 전체가 아닌 필요한 레코드를 잠글 수 있기 때문에, 여러 요청이 동시에 들어오는 상황에서도 서로 다른 레코드에 대한 작업을 함께 처리할 수 있습니다.
  • 다만 레코드 수준의 잠금이라고 해서, 실제로 수정할 레코드만 잠기는 것은 아니었습니다.
  • 이 부분은 뒤에서 인덱스와 잠금을 같이 보면서 다시 정리하게 되었습니다.

프라이머리 키에 의한 클러스터링

  • InnoDB는 PK가 있으면 이를 클러스터드 인덱스로 사용하며, 그 인덱스의 리프 페이지에 실제 레코드가 저장됩니다.
  • 레코드는 PK 값의 순서로 정렬되어 관리되는데, 이것을 디스크의 모든 위치가 PK 순서대로 연속해서 배치된다는 의미로 이해하면 안 될 것 같습니다.
  • 세컨더리 인덱스에는 레코드의 물리적인 주소 대신 PK 값이 들어갑니다.
  • 그래서 세컨더리 인덱스로 검색한 뒤, 실제 레코드가 필요하면 PK를 이용해 클러스터드 인덱스를 다시 검색하는 구조입니다.
  • PK가 없는 경우에는 인덱스를 구성하는 모든 컬럼이 NOT NULL인 첫 번째 유니크 인덱스를 사용하고, 그것도 없다면 내부적으로 숨겨진 클러스터드 인덱스를 생성합니다.

외래 키 지원

  • InnoDB는 외래 키를 지원하며, 부모 테이블과 자식 테이블 사이의 참조 관계를 확인해줍니다.
  • 다만 관계를 확인하는 과정에서도 잠금이 필요하기 때문에, 외래 키가 단순히 데이터의 관계만 표현하는 것은 아니라는 생각이 들었습니다.

MVCC와 잠금 없는 일관된 읽기

  • MVCC는 Multi Version Concurrency Control의 약자로, 하나의 레코드에 대해 여러 버전을 관리하는 방식입니다.
  • InnoDB는 변경 이전의 데이터를 복원하는 데 필요한 정보를 언두 로그에 남기고, 조회하는 트랜잭션에 맞는 버전을 보여줍니다.
  • 예를 들어 다른 트랜잭션에서 데이터를 수정하고 있더라도, 일반 SELECT에서는 수정이 끝날 때까지 기다리는 대신 자신이 볼 수 있는 이전 버전을 읽을 수 있습니다.
  • 이렇게 읽기와 쓰기가 서로를 불필요하게 기다리지 않도록 하는 것이 잠금 없는 일관된 읽기라고 이해했습니다.
  • 다만 모든 SELECT가 같은 방식으로 동작하는 것은 아닙니다.
  • READ COMMITTED와 REPEATABLE READ의 일반 SELECT는 일관된 읽기를 사용하지만, SELECT ... FOR UPDATE 같은 잠금 조회는 실제로 잠금을 획득합니다.
  • READ UNCOMMITTED는 커밋되지 않은 변경도 읽을 수 있어서, 일관된 읽기와는 구분해야 합니다.
  • 이 부분을 읽으면서 버퍼 풀과 데이터 파일이 항상 같은 상태라고 생각하면 안된다는 것도 알게 되었습니다.
  • 메모리에서 변경된 내용은 나중에 데이터 파일에 기록될 수 있으며, 그 사이의 복구를 위해 리두 로그 같은 장치가 필요합니다.

자동 데드락 감지와 장애 복구

  • 서로 다른 트랜잭션이 상대방의 잠금이 풀리기만 기다리면, 어느 쪽도 작업을 진행하지 못하는 데드락이 발생할 수 있습니다.
  • InnoDB는 데드락 감지가 활성화되어 있으면 이를 감지하고, 트랜잭션 하나를 롤백하여 대기 상태를 풀어줍니다.
  • 이때 삽입·수정·삭제한 행의 수가 적은 트랜잭션을 우선 선택하려고 합니다.
  • 상대적으로 되돌려야 하는 작업이 적기 때문이라고 이해했습니다.
  • 또한 서버가 비정상적으로 종료되더라도 데이터를 복구할 수 있도록 여러 장치를 가지고 있습니다.
  • 리두 로그, 언두 로그, Doublewrite Buffer가 각각 어떤 역할을 하는지 같이 봐야 이해가 되는 부분이었던 것 같습니다.

InnoDB 버퍼 풀

  • 버퍼 풀은 데이터와 인덱스의 페이지를 메모리에 캐시해두는 공간입니다.
  • 자주 사용하는 데이터를 매번 디스크에서 읽지 않고 메모리에서 가져올 수 있으며, 변경된 페이지를 모아서 나중에 디스크에 기록하는 역할도 합니다.
  • 단순히 읽기를 빠르게 해주는 캐시라고만 생각했는데, 쓰기 작업을 처리하는 과정에서도 중요한 역할을 하고 있었습니다.

Doublewrite Buffer

  • 데이터 페이지를 파일에 쓰는 도중 장애가 발생하면, 페이지의 일부만 기록될 수 있습니다.
  • Doublewrite Buffer는 실제 데이터 파일에 페이지를 기록하기 전에 별도의 공간에 먼저 기록해두고, 이런 상황에서 정상적인 페이지를 복구할 수 있게 해주는 장치입니다.
  • 이름만 봤을 때는 데이터를 두 번 쓰는 것이 비효율적인 게 아닐까 싶었지만, 페이지가 불완전하게 기록되는 상황에 대비하기 위한 것이었습니다.

언두 로그와 리두 로그

  • 처음엔 둘 다 로그라서 비슷한 역할을 하는 것 같았는데, 필요한 이유가 달랐습니다.
  • 언두 로그: 변경 이전의 데이터를 복원하기 위한 정보이며, 롤백과 MVCC에 사용
  • 리두 로그: 변경 내용을 다시 적용하기 위한 정보이며, 장애 발생 후 복구에 사용
  • 로그 버퍼: 리두 로그를 디스크에 기록하기 전에 메모리에 모아두는 공간
  • 언두 로그는 변경을 되돌리거나 이전 버전을 읽기 위한 것이고, 리두 로그는 데이터 파일에 반영되지 못한 변경을 복구하기 위한 것이라고 정리했습니다.

체인지 버퍼

  • 체인지 버퍼는 세컨더리 인덱스의 페이지가 버퍼 풀에 없을 때, 변경 내용을 따로 모아두었다가 나중에 해당 페이지에 반영하는 구조입니다.
  • 변경할 때마다 디스크에서 인덱스 페이지를 읽어오는 작업을 줄이기 위해 사용합니다.
  • 다만 모든 인덱스에 사용할 수 있는 것은 아니며, 일반적으로 중복 확인이 필요하지 않은 비유니크 세컨더리 인덱스의 변경에 사용됩니다.
  • 메모리뿐 아니라 디스크에도 유지되는 구조라서, 단순한 임시 메모리 공간이라고만 이해하면 부족할 것 같습니다.

어댑티브 해시 인덱스

  • InnoDB가 자주 사용하는 검색 패턴을 확인하고, 도움이 된다고 판단하면 자동으로 만드는 해시 인덱스입니다.
  • B-Tree를 매번 탐색하는 비용을 줄이기 위한 기능이며, innodb_adaptive_hash_index 설정으로 제어할 수 있습니다.
  • 자동으로 만들어준다고 해서 모든 상황에서 성능이 좋아지는 것은 아니고, 요청의 특성에 따라 잠금 경합 등 추가 비용이 생길 수도 있습니다.
  • 결국 이런 기능들도 이름과 목적만 보고 좋다고 판단하기보다는, 실제 사용하는 상황을 같이 봐야 하는 것 같습니다.
  • 여기까지가 엔진에 대한 내용입니다...
  • 생소한 내용이 너무 많아서, 이런 것도 모른 채로 작업을 하고 있었구나...라는 생각이 들었습니다.
  • 그리고 지금까지의 실무와 조금 더 직접적으로 연결된다고 생각한 인덱스와 트랜잭션, 잠금도 같이 공부해보았습니다.

인덱스

  • 책에서는 인덱스를 SortedList와 ArrayList에 빗대어 설명하고 있었습니다.
  • 정렬된 상태로 데이터를 유지하면 원하는 값을 빠르게 찾을 수 있지만, 데이터를 추가하거나 변경할 때는 그 정렬 상태를 유지하기 위한 비용이 필요합니다.
  • 인덱스도 비슷하게, 데이터를 저장하고 변경하는 성능의 일부를 희생하여 읽기 성능을 높이는 구조라고 이해했습니다.
  • 그래서 조회가 빠르다는 이유만으로 인덱스를 많이 만드는 것이 좋은 것은 아니었습니다.

B-Tree 인덱스

  • B-Tree는 균형을 유지하는 트리 구조이며, 루트 노드와 브랜치 노드, 리프 노드로 구성됩니다.
  • InnoDB에서는 클러스터드 인덱스의 리프 페이지에 실제 레코드가 들어있습니다.
  • 세컨더리 인덱스로 실제 레코드를 읽는 과정은 다음과 같습니다.
  • 세컨더리 인덱스에서 조건에 맞는 값과 PK를 찾습니다.
  • 찾은 PK를 이용해 클러스터드 인덱스를 검색합니다.
  • 클러스터드 인덱스의 리프 페이지에서 레코드를 읽습니다.
  • 다만 조회에 필요한 컬럼이 세컨더리 인덱스에 모두 들어있다면, 실제 레코드를 추가로 읽지 않는 커버링 인덱스 방식으로 처리할 수도 있습니다.
  • 그래서 세컨더리 인덱스를 사용하면 무조건 두 번 검색한다고 이해하는 것은 정확하지 않았습니다.

인덱스 키의 추가·삭제·변경

  • 인덱스 키를 추가할 때는 B-Tree에서 들어갈 위치를 찾고, 필요하면 페이지를 분리하면서 상위 노드까지 변경합니다.
  • 단순히 값을 하나 넣는 것보다 더 많은 작업이 생길 수 있습니다.
  • 삭제할 때는 우선 삭제 표시를 남기고, 나중에 더 이상 필요하지 않을 때 정리합니다.
  • 키 값을 변경하는 경우에는 기존 값을 삭제하고 새로운 값을 추가하는 방식으로 처리합니다.
  • 이 과정을 보니, 인덱스가 많은 테이블에서 쓰기 작업의 비용이 커지는 이유도 조금은 이해가 되었습니다.

인덱스 검색

  • 인덱스가 있다고 해서 모든 검색에 사용할 수 있는 것은 아닙니다.
  • 인덱스가 있는 컬럼에 함수나 연산을 적용하면, 기존 인덱스의 정렬 순서를 그대로 이용하기 어려울 수 있습니다.
  • 함수 기반 인덱스 등 별도의 대응 방법도 있지만, 우선은 쿼리에서 해당 인덱스를 실제로 사용할 수 있는지 확인하는 것이 중요하다고 생각했습니다.
  • 그리고 인덱스는 조회 성능뿐 아니라 UPDATE와 DELETE에서 잠금의 범위에도 영향을 줍니다.
  • 이 부분은 인덱스를 공부하면서 가장 다시 생각해보게 된 내용이었습니다.

다중 컬럼 인덱스와 정렬 순서

  • 다중 컬럼 인덱스는 두 개 이상의 컬럼으로 구성된 인덱스입니다.
  • 첫 번째 컬럼을 기준으로 정렬하고, 첫 번째 컬럼의 값이 같을 때 두 번째 컬럼을 기준으로 정렬합니다.
  • 그래서 같은 컬럼들이 들어있더라도, 컬럼의 순서에 따라 사용할 수 있는 검색 조건이 달라집니다.
  • 단순히 자주 사용하는 컬럼을 모아두는 것만으로는 부족하고, 실제 쿼리의 조건을 보고 순서를 정해야 하는 것 같습니다.
  • 또한 인덱스의 컬럼은 오름차순이나 내림차순으로 정의할 수 있고, 스캔 방향도 달라질 수 있습니다.
  • ORDER BY가 있을 때는 인덱스의 컬럼 순서와 정렬 방향이 쿼리와 어떻게 맞는지도 확인해야 합니다.

유니크 인덱스와 외래 키

  • 유니크 인덱스는 검색을 빠르게 해주는 역할과 함께, 값의 중복을 막는 제약 조건의 역할도 합니다.
  • 다만 NULL을 허용하는 컬럼이라면 NULL은 여러 개 들어갈 수 있습니다.
  • 중복을 허용해야 하는 컬럼에 유니크 인덱스를 사용할 수는 없으니, 검색 성능만을 위해서라면 일반 세컨더리 인덱스를 검토해야 합니다.
  • 외래 키도 인덱스와 연결됩니다.
  • InnoDB는 외래 키를 확인하기 위한 인덱스를 필요로 하고, 부모나 자식의 관련 데이터를 변경할 때 참조 관계를 확인하는 과정에서 잠금 대기가 발생할 수 있습니다.
  • 관계만 선언하면 끝나는 것이 아니라, 실제 변경 과정에서 어떤 영향을 주는지도 알아야겠다는 생각이 들었습니다.

트랜잭션

  • 트랜잭션은 작업의 완전성을 보장해주는 것
  • 하나의 논리적인 작업이 전부 적용되거나, 전부 적용되지 않도록 보장하는 것입니다.
  • 중간에 일부만 처리된 상태인 partial update가 남지 않도록 해주는 것이라고 이해했습니다.
  • 잠금과 트랜잭션은 같이 이야기되는 경우가 많지만, 각각 필요한 이유를 구분해서 생각해보았습니다.
  • 잠금: 여러 요청이 동시에 같은 데이터에 접근할 때 충돌을 제어
  • 트랜잭션: 여러 변경을 하나의 작업으로 묶고, 실패하면 되돌려 작업의 완전성을 보장
  • 다만 트랜잭션으로 묶었다는 것만으로 모든 동시성 문제가 해결되는 것은 아닙니다.
  • 실제로 어떤 데이터를 읽고 잠그는지는 격리 수준과 쿼리도 함께 봐야 합니다.

MySQL에서의 트랜잭션

  • 예를 들어 PK가 3인 데이터가 이미 있는 상태에서, 하나의 일반 INSERT 문으로 PK 1, 2, 3을 순서대로 추가한다고 가정해보았습니다.
  • MyISAM이나 MEMORY에서는 1, 2가 저장된 뒤 3에서 중복 오류가 발생하면, 앞에서 저장한 데이터가 남을 수 있습니다.
  • InnoDB에서는 해당 INSERT 문이 실패하면, 그 문장에서 추가하려던 1, 2도 함께 롤백됩니다.
  • 같은 SQL을 실행하더라도 스토리지 엔진에 따라 결과가 달라질 수 있다는 점이 인상적이었습니다.
  • 트랜잭션을 지원하지 않는 엔진에서는 일부만 반영된 데이터를 어떻게 처리할지도 애플리케이션에서 고려해야 합니다.
  • 그리고 트랜잭션의 범위는 꼭 필요한 최소한의 작업으로 잡아야 합니다.
  • 트랜잭션 안에 오래 걸리는 작업이 들어가면, 그동안 커넥션과 잠금을 유지하면서 다른 요청에도 영향을 줄 수 있기 때문입니다.

MySQL 엔진의 잠금

  • 잠금도 모두 같은 범위로 적용되는 것이 아니었습니다.
  • 우선 MySQL 엔진에서 제공하는 잠금들을 정리해보았습니다.

글로벌 락

  • 글로벌 락은 MySQL 서버 전체에 영향을 주는 잠금입니다.
  • 한 세션에서 획득하면 다른 세션의 대부분의 DDL과 데이터 변경 작업이 대기하며, 다른 데이터베이스를 사용하더라도 영향을 받습니다.

테이블 락

  • 개별 테이블 단위로 설정하는 잠금이며, 명시적으로 획득할 수 있습니다.
  • MyISAM이나 MEMORY에서는 데이터 변경 시 테이블 수준의 잠금을 사용합니다.
  • InnoDB는 일반적인 데이터 변경에 레코드 수준의 잠금을 사용합니다.
  • 다만 테이블 수준의 잠금이 아예 없는 것은 아니고, 명시적인 테이블 락이나 레코드 잠금과 함께 사용하는 의도 잠금 등이 있습니다.

네임드 락

  • GET_LOCK() 함수로 임의의 문자열에 대해 획득하는 잠금입니다.
  • 테이블이나 레코드 대신, 여러 클라이언트가 약속한 이름을 기준으로 작업을 동기화할 수 있습니다.
  • 이름을 기준으로 잠금을 건다는 점이 생소했는데, 데이터 한 건의 변경보다 더 넓은 작업을 조율해야 하는 상황에서 사용할 수 있겠다는 생각이 들었습니다.

메타데이터 락

  • 테이블 등의 구조를 보호하기 위한 잠금입니다.
  • 테이블의 이름이나 구조를 변경할 때뿐 아니라, SELECT나 데이터 변경으로 테이블을 사용하는 동안에도 자동으로 획득합니다.
  • 그래서 어떤 트랜잭션이 테이블을 사용하고 있다면, 다른 세션의 ALTER TABLE이 그 트랜잭션이 끝날 때까지 기다릴 수 있습니다.
  • 데이터를 수정하지 않는 조회도 구조 변경에는 영향을 줄 수 있다는 점을 같이 알아두어야 할 것 같습니다.

InnoDB 스토리지 엔진의 잠금

  • InnoDB의 잠금에서는 레코드뿐 아니라, 레코드 사이의 간격도 잠글 수 있다는 점이 생소했습니다.

레코드 락

  • 레코드 하나에 대한 잠금이지만, 내부적으로는 테이블의 레코드 자체가 아닌 인덱스의 레코드를 잠급니다.
  • 명시적으로 만든 인덱스가 없는 테이블도 내부의 숨겨진 클러스터드 인덱스를 사용해 잠금을 설정합니다.
  • PK나 유니크 인덱스의 전체 키를 동등 조건으로 검색하여 존재하는 레코드 하나를 특정할 때는, 그 레코드만 잠그고 앞의 간격은 잠그지 않을 수 있습니다.
  • 그래서 유니크 인덱스가 있다는 사실만 볼 것이 아니라, 어떤 조건으로 검색했는지도 같이 봐야 합니다.

갭 락

  • 인덱스 레코드와 인접한 레코드 사이의 간격을 잠그는 것입니다.
  • 기존 레코드를 수정하지 못하게 하는 것보다는, 해당 간격에 새로운 레코드가 들어오는 것을 막기 위한 잠금입니다.

넥스트 키 락

  • 레코드 락과 그 레코드 앞의 갭 락을 합친 형태입니다.
  • InnoDB의 기본 격리 수준인 REPEATABLE READ에서는 잠금 조회나 UPDATE·DELETE의 범위 검색에 사용하여, 검색한 범위에 다른 트랜잭션이 새로운 레코드를 넣는 것을 막습니다.
  • 지금 있는 데이터만 잠그면 된다고 생각하기 쉬운데, 같은 조건으로 다시 조회할 때 새 데이터가 나타나는 상황까지 고려해야 한다는 것이었습니다.

자동증가 락

  • AUTO_INCREMENT 값을 할당하는 과정에서 사용하는 특별한 테이블 수준의 잠금입니다.
  • 다만 INSERT를 실행할 때 항상 같은 방식으로 테이블을 잠그는 것은 아니며, innodb_autoinc_lock_mode 설정과 INSERT의 형태에 따라 동작이 달라집니다.

인덱스와 잠금

  • 이 부분이 이번에 공부하면서 가장 기억에 남았습니다.
  • InnoDB는 인덱스의 레코드를 잠그기 때문에, 최종적으로 수정하는 데이터의 수와 잠그는 데이터의 수가 같지 않을 수 있습니다.
  • 예를 들어 다음과 같은 상황이라고 가정해보았습니다.
first_name이 '조'인 데이터: 253개
그중 last_name이 '성준'인 데이터: 1개
사용할 수 있는 인덱스: first_name에만 존재

UPDATE users
SET last_name = '성준(수정)'
WHERE first_name = '조'
  AND last_name = '성준';
  • 실제로 수정하려는 데이터는 한 건입니다.
  • 하지만 first_name 인덱스로 '조'인 데이터를 찾은 뒤 last_name을 확인해야 하므로, 검색 과정에서는 253개의 레코드를 확인하게 됩니다.
  • 기본 격리 수준인 REPEATABLE READ에서 이 인덱스를 사용하는 실행 계획이라면, 최종 조건에 맞는 한 건뿐 아니라 검색한 레코드들까지 잠글 수 있습니다.
  • 범위에 따라 갭 락이나 넥스트 키 락도 함께 걸릴 수 있고, READ COMMITTED에서는 조건에 맞지 않는 레코드의 잠금을 해제하는 등 차이가 있습니다.
  • 만약 사용할 수 있는 인덱스가 없다면...테이블 전체를 검색하면서 모든 레코드에 잠금을 걸 수도 있습니다.
  • 인덱스는 조회를 빠르게 하기 위해 사용하는 것이라고 생각했는데, 동시성 처리에도 이렇게 직접적인 영향을 주고 있었습니다.
  • 단순히 수정하는 데이터가 한 건이라는 이유로 잠금의 범위도 작을 것이라고 생각하면 안된다는 것을 알게 되었습니다.

MySQL의 격리 수준

  • 격리 수준을 보기 전에, 트랜잭션이 동시에 실행될 때 발생할 수 있는 현상부터 정리해보았습니다.
  • DIRTY READ: 다른 트랜잭션이 아직 커밋하지 않은 변경을 읽는 현상
  • NON-REPEATABLE READ: 같은 트랜잭션에서 같은 레코드를 다시 읽었을 때 값이 달라지는 현상
  • PHANTOM READ: 같은 트랜잭션에서 같은 범위 조건으로 다시 조회했을 때, 다른 트랜잭션의 변경으로 결과에 포함되는 행이 달라지는 현상
격리 수준 DIRTY_READ NON_REPEATABLE_READ PHANTOM_READ
READ_UNCOMMITTED 발생 발생 발생
READ_COMMITTED 없음 발생 발생
REPEATABLE_READ 없음 없음 발생 (InnoDB는 거의 없음)
SERIALIZABLE 없음 없음 없음

READ UNCOMMITTED

  • 다른 트랜잭션이 커밋하지 않은 변경도 읽을 수 있어서 DIRTY READ가 발생할 수 있습니다.
  • 읽은 데이터가 나중에 롤백될 수도 있으니, 그 값을 기준으로 다음 작업을 판단하는 것은 위험할 수 있겠다는 생각이 들었습니다.

READ COMMITTED

  • 다른 트랜잭션이 커밋한 데이터만 읽습니다.
  • 다만 일반 SELECT를 실행할 때마다 새로운 스냅샷을 사용하므로, 같은 트랜잭션 안에서 두 번 조회하더라도 중간에 다른 트랜잭션이 커밋하면 결과가 달라질 수 있습니다.
  • 그래서 금전적인 처리처럼 읽은 값을 기준으로 다음 작업을 결정해야 하는 상황에서는, 이 격리 수준만으로 충분한지 잠금이나 갱신 방식도 함께 검토해야 합니다.

REPEATABLE READ

  • InnoDB의 기본 격리 수준입니다.
  • 일반 SELECT는 첫 번째 일관된 읽기에서 만들어진 스냅샷을 계속 사용하므로, 다른 트랜잭션이 커밋하더라도 같은 기준으로 조회할 수 있습니다.
  • 다만 자신의 트랜잭션에서 변경한 내용은 조회에 반영됩니다.
  • 처음 정리할 때는 PHANTOM READ가 발생한다는 내용과, 갭 락과 넥스트 키 락 덕분에 발생하지 않는다는 내용이 같이 있어서 헷갈렸습니다.
  • 일반 SELECT에서는 같은 스냅샷을 사용해 다른 트랜잭션이 추가한 행이 새로 보이는 것을 막고, 잠금 조회나 UPDATE·DELETE의 범위 검색에서는 갭 락과 넥스트 키 락으로 해당 범위의 삽입을 막습니다.
  • 다만 일반 SELECT와 최신 상태를 보는 잠금 조회·변경 작업을 섞으면, 서로 다른 기준의 데이터를 볼 수 있다는 점을 주의해야 합니다.
  • 단순히 '언두 로그에는 잠금을 걸 수 없어서 PHANTOM READ가 발생한다'고 외우기보다는, 지금 실행하는 쿼리가 어떤 방식으로 읽는지를 구분해야겠다고 생각했습니다.

SERIALIZABLE

  • 가장 엄격한 격리 수준입니다.
  • autocommit을 끈 상태에서는 일반 SELECT도 공유 잠금을 획득하여, 다른 트랜잭션의 충돌하는 변경 작업을 기다리게 합니다.
  • 공유 잠금끼리는 함께 읽을 수 있으므로, 다른 트랜잭션이 해당 레코드에 절대 접근할 수 없다는 의미는 아닙니다.
  • 더 엄격하게 처리하는 만큼 잠금 대기와 동시성에 대한 비용도 커질 수 있습니다.
  • 격리 수준이 높으면 무조건 좋다거나, REPEATABLE READ가 있으니 필요 없다고 생각하기보다는 요구사항과 실행하는 쿼리를 보고 판단해야 하는 것 같습니다.

짧은 회고

  • 이번에는 동시성 과제를 위해 책을 읽기 시작했는데, 읽다보니 MySQL 내부에서 데이터를 어떻게 저장하고 읽는지부터 다시 공부하게 되었습니다.
  • InnoDB라는 이름은 알고 있었지만, 그 이름을 안다는 것과 실제 동작을 이해한다는 것은 많이 달랐던 것 같습니다.
  • 특히 인덱스에 따라 잠금의 범위가 달라진다는 부분을 보면서, 애플리케이션에서 어떤 락을 사용할지만 고민하면 되는 것이 아니었다는 생각이 들었습니다.
  • 같은 UPDATE라도 사용하는 인덱스와 격리 수준에 따라 다른 요청에 미치는 영향이 달라질 수 있기 때문입니다.
  • 2주차에는 기능과 구현의 편의성만 보고 테이블의 성격을 놓쳤다면, 이번에는 쿼리가 원하는 결과를 반환한다는 것만 보고 내부 동작을 놓치고 있었던 것은 아닐까...라는 생각이 들었습니다.
  • 아직 각 기능을 모두 이해했다고 말하기에는 부족하지만, 앞으로 동시성 문제를 볼 때는 쿼리와 인덱스, 트랜잭션의 범위를 같이 확인해야겠다는 기준은 생긴 것 같습니다.
  • 말로 설명하지 못하는 지식을 다시 공부해야 한다는 것을, 이번에도 한번 더 느끼게 되었습니다.
